---
description: Sole independent review of uncommitted changes - reviewer audits, approved fixes are applied and validated, then an approved commit plan is executed (local commits only)
argument-hint: "[--handoff <path>] [additional repos]"
agents: reviewer, worker, commit-planner
---
Execute this workflow. This is the modular sequence's **sole review and commit
step**: it picks up the uncommitted changes left behind by an implementation
run (or any existing changes) and owns review, approved fixes, revalidation, and
the local commit. Never push, never open a PR.

1. **Find all repos with changes.** Treat the current working directory as the default search root. **Discover nested repository roots first** (subfolders containing their own `.git` metadata) beneath the current repository; do not inspect sibling checkouts or other paths unless the user explicitly lists them as arguments in $@ (excluding any `--handoff <path>` value — a handoff file is not a repository).

   **Classify paths before touching them.** Assign every changed path to its **deepest owning repository** (paths inside a nested repo belong to that nested repo, not the parent); exclude nested-root paths from the parent repository's changed-file list **unless** the parent intentionally tracks the gitlink. Using each repo's ignore rules plus an explicit sensitive-file policy (`.env*`, credential/token/key files, `auth.json` and other auth or config secrets), classify every changed path **before opening it**: read only safe untracked files, skip and never read sensitive files (record them as excluded), and **ask the user before inspecting ambiguous files**.

   Then, for **each** discovered or explicitly listed repository, run `git status --short` and inspect the actual changes in all three categories: `git diff` (unstaged), `git diff --cached` (staged), and the safe untracked files (`??` entries in `git status --short`). **Capture and classify pre-existing staged and unstaged hunks during discovery** so later patch-level staging can distinguish related from unrelated work. Produce the complete list of `{repo root, changed files}` pairs where the changed-file list covers **all three categories** and uses the deepest-owning-repo attribution. Sensitive files are excluded from the discovery list and from every downstream hand-off to the reviewer or worker.

   **Optional implementation handoff:** if the user supplies `--handoff <path>` in $@ (or pastes a handoff summary from a previous implementation run), **read the file first** and interpolate its contents — approved plan and scope, changed files, validation commands and results, known limitations — into your analysis as helpful orientation only. It **never replaces diff inspection**: always discover/verify the repositories and inspect the actual diff yourself, and reconcile any mismatch between the handoff claims and the real changes before continuing. **The resolved handoff path is excluded from repository changes and from review/commit scope by default**; include it only after an explicit user choice.

2. **Review each repo with the `reviewer` agent — in parallel.** The reviewer is a bg agent (`pane: false`), so the subagent tool awaits its real output. Dispatch one task per repo with `agentScope: "both"` (the agent is user-level):

   - `cwd`: the repo root
   - task: a string that **interpolates** (a) the exact changed-file list from step 1 covering unstaged, staged, and untracked files, and (b) the handoff summary contents if one exists, plus the instruction: "Review the current uncommitted changes in <repo root>. Changed files: <exact file list>. This file list is the source of truth — do not re-run git reconnaissance beyond confirming the diff. Return your standard severity-ranked findings (critical / warnings / suggestions)."

   This is the **sole independent review** — no other review step runs elsewhere in the modular sequence, so the reviewer covers the changes in full.

   **Reviewer gate (stop on failure):** this phase requires **one successful, complete reviewer result per repository**. If any reviewer dispatch fails, returns an incomplete result, or a repo ends up without full review coverage, **stop**: report which repositories were reviewed and which were not (partial coverage), and do not apply fixes or create a commit plan until the user approves a retry.

3. **Present the findings and ask which fixes to apply.** Show each repo's review summary to the user and ask what to apply before committing (options: all findings / critical+warnings / critical only / selected items / none — commit as-is). If none or declined, skip to the commit plan with the findings recorded as follow-ups.

4. **Apply the approved fixes with the `worker` agent (pane agent), then validate.** For each repo with approved fixes, dispatch one worker per repo with `agentScope: "both"` and `cwd` set to the repo root. **Process workers sequentially: one repo at a time** — dispatch the next repo's fix worker only after the previous one has completed and its result was collected. The dispatch is standalone (no {previous} placeholder available), so **interpolate the approved findings into the dispatch's `task` string** — they are the source of truth; the worker must not re-run the review. Instruct the worker to: apply **only the approved fixes** and ask before any scope change; **preserve unrelated index state — never stage or unstage anything, and do not disturb pre-existing staged or unstaged hunks**; then run the repository's relevant validation commands (tests, typecheck, lint, format, repo validation) and report real pass/fail output; and never commit, push, or open a PR at this stage. **END YOUR TURN** — the worker runs in its visible pane and the completion arrives as a follow-up message that wakes you.

   On wake, collect the result (use the wake payload / `get_subagent_result` on the saved taskId). **Validation gate (stop on failure):** verify the fixes with concrete validation output — rerun the key commands yourself if the evidence is thin. If validation fails, stop and report the failure honestly; do not build a commit plan on a failing build and do not retry without asking.

5. **Create the final commit plan with the `commit-planner` agent (bg agent).** Only after the fixes pass validation, dispatch the `commit-planner` agent (single dispatch, bg agent — the tool awaits its real output) with `agentScope: "both"` and `cwd` set to the repo root. Interpolate into the dispatch's `task` string: the exact changed-file list from step 1, the approved review findings and which were applied, the validation results from step 4, and the no-fix validation rule context if applicable. The commit-planner produces the executable commit plan per repo: dependency-ordered commit groups with exact files and hunks, conventional commit types, proposed messages, required cleanup, focused tests, and the exact execution checklist with validation order — the checklist must cover the applicable validation categories: **unit tests, E2E / visual regression tests (if the change affects UI, user flows, or rendering), accessibility checks (if the change touches HTML, JSX, TSX, Vue, or any rendered output), documentation checks (if the change affects public APIs, CLI, config, or user-facing behavior), type checking (if the repo uses TypeScript), linting, formatting, and other repo-specific validation (any project-defined checks)** — with the narrowest applicable command per category per repo (including the narrowest applicable command for other repo-specific validation), and each commit group must explicitly mark **every** category as either **applicable with the exact command** or **not applicable with a short reason ("N/A — reason")** so omissions are detectable during review. This is a standalone dispatch with no {previous} placeholder — interpolate all context into the task string. The returned plan must state, per commit group, whether tests and docs apply and the rule that decides it, and include a `## Blocking gaps` section only when an applicable artifact is missing.

   **Blocking-gap gate (stop on missing artifacts):** if the plan reports any entry under `## Blocking gaps` — an applicable test or doc that is missing — do not present it for approval and do not commit. Dispatch a `worker` to add the missing tests or documentation, re-run the relevant validation, then re-dispatch the `commit-planner` so the revised plan reflects the closed gaps. Treat an `N/A` that names no deciding rule the same way. Absence of the section means nothing was required and is not a failure.

   **Reviewer gate for the commit plan:** after the commit-planner returns with no blocking gaps, present the plan to the user and get explicit approval before any commit. If the user requests changes, re-dispatch the commit-planner with the amendments and present the revised plan.

   **No-fix validation rule:** if the user selected **no fixes** in step 3, the commit plan must explicitly record that **validation was not run during a fix phase**, and step 6's commit worker must run the repository's relevant validation commands at the start of the plan's order — **validating the working tree before staging and validating the staged tree before committing** — treating a failure exactly like the step 4 gate (stop and report). When fixes were applied, the plan instead records which validation already passed in step 4, and the worker still reruns the checks at the same points in the order.

6. **Execute the approved commit plan with the `worker` agent (pane agent).** Dispatch one worker per repo with `agentScope: "both"` and `cwd` set to the repo root, processing **sequentially — one repo at a time**, dispatching the next repo only after the previous repo's commits are confirmed. The dispatch is standalone (no {previous} placeholder available), so **interpolate the approved commit plan into the dispatch's `task` string** — it is the source of truth; the worker must not re-run the analysis. Instruct the worker to: follow the plan exactly and ask before any scope change; **stage at patch level (`git add -p` or equivalent), staging only the hunks planned for that commit group — never whole files that contain unrelated hunks — and preserve unrelated index state**; then execute every group in the plan's exact order: **validate the working tree → stage the intended hunks → immediately inspect the staged patch (`git status`, `git diff --cached`) and verify that only planned files and hunks are staged (unstage anything unplanned) → validate the staged tree → commit**; run the listed validation commands and treat any failure as the step 4 gate (stop and report); and never push. **END YOUR TURN** — the worker runs in its visible pane and the completion arrives as a follow-up message that wakes you.

7. **On wake, report per repo** (use the wake payload / `get_subagent_result` on the saved taskId): what was committed, which checks ran, and anything the worker flagged. If the worker failed or stopped on a check failure, report the failure honestly and do not retry without asking.

If the user prefers not to use a worker, offer to execute the approved fixes or commit plan directly in this session instead — but ask first; delegation is the default.
